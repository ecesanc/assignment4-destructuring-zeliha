## Field guide

### Form 1: array values by position

**Syntax:** `const [x, y] = makePair()`

**Example:** In `js/arrays.mjs`, `minMax([14, 3, 27])` returns `[3, 27]`, and `const [lowest, highest]` takes the first value into `lowest` and the second into `highest`.

**Output:** `form 1: 3 27`

**Use it when:** a function returns a fixed-order tuple-like array.

**Watch out:** position controls meaning; swapping the order changes the result. A missing position becomes `undefined` unless a default is used.

### Form 2: skip and collect the rest

**Syntax:** `const [, second, ...others] = list`

**Example:** With `['intro', 'Midnight City', 'Afterglow', 'Northern Lights', 'Finale']`, the first item is skipped, the second is named, and the remaining items are collected.

**Output:** `form 2: Midnight City [ 'Afterglow', 'Northern Lights', 'Finale' ]`

**Use it when:** the first position is irrelevant and the remainder should become a new array.

**Watch out:** the three dots are **rest** in a pattern: they collect remaining values. This is different from spread, which expands values in an expression.

### Form 3: swap variables

**Syntax:** `[a, b] = [b, a]`

**Example:** `currentPage` starts as `3` and `lastPage` as `8`. The right side is evaluated first, then the two variables are assigned in the new order.

**Output:** `form 3: 8 3`

**Use it when:** two already-declared variables need to exchange values without a temporary variable.

**Watch out:** because the left side is an assignment, it needs parentheses at the beginning of a statement; otherwise `{}` or `[]` can be parsed in an unexpected context. A semicolon before it is also useful when the previous line could be joined by automatic semicolon insertion.

### Form 4: array defaults

**Syntax:** `const [a = 1, b = 2] = values`

**Example:** `const [firstTag = 'untagged', secondTag = 'general'] = ['study']`.

**Output:** `form 4: study general`

**Use it when:** a missing array position should receive a meaningful fallback.

**Watch out:** the default runs only for `undefined`, not for `null`. The default for `secondTag` is used because that position is absent.

### Form 5: object properties by name

**Syntax:** `const { a, b } = object`

**Example:** From `{ id: 't1', title: 'Plan study session', status: 'todo' }`, `const { title, status } = task` selects properties by their names.

**Output:** `form 5: Plan study session todo`

**Use it when:** the property names already communicate clearly what the local variables mean.

**Watch out:** object order does not matter, but the property must have the requested name. A missing property produces `undefined`.

### Form 6: rename a property

**Syntax:** `const { sourceName: localName } = object`

**Example:** `const { title: heading } = book` reads the `title` property but creates the local variable `heading`.

**Output:** `form 6: The Left Hand of Darkness`

**Use it when:** a local name would otherwise collide with another variable or a clearer name is needed.

**Watch out:** `title` is the source property name, not a variable created by this pattern. Only `heading` exists afterward.

### Form 7: object defaults

**Syntax:** `const { property = fallback } = object`

**Example:** `settings` has a `theme` but no `density`, so `const { density = 'comfortable' } = settings` supplies the fallback.

**Output:** `form 7: comfortable`

**Use it when:** an optional setting should become a concrete local value.

**Watch out:** like array defaults, this replaces only `undefined`. If the object contains `{ density: null }`, the result is still `null`.

### Form 8: object rest

**Syntax:** `const { chosen, ...others } = object`

**Example:** `const { id, ...taskDetails } = { id: 't7', title: 'Submit report', priority: 'high' }` separates the identifier from the other own enumerable properties.

**Output:** `form 8: t7 { title: 'Submit report', priority: 'high' }`

**Use it when:** one or more fields are handled specially and the remaining fields should be forwarded or grouped.

**Watch out:** `others` is a new shallow object. It does not contain `id`, and nested values inside it are still references to the original nested values.

### Form 9: nested patterns

**Syntax:** `const { parent: { child }, list: [first] } = object`

**Example:** From `{ owner: { name: 'Mina' }, labels: ['urgent', 'school'] }`, the pattern reaches into the nested owner object and the labels array.

**Output:** `form 9: Mina urgent`

**Use it when:** the data shape is stable and extracting several deeply related values makes the code clearer.

**Watch out:** every intermediate object/array must exist. A missing `owner` would throw while trying to destructure `name`; optional chaining or a default object may be safer for uncertain data.

### Form 10: computed property key

**Syntax:** `const { [key]: value } = object`

**Example:** When `selectedField` is `'priority'`, `const { [selectedField]: selectedValue } = record` reads `record.priority`.

**Output:** `form 10: priority high`

**Use it when:** the property to extract is stored in a variable instead of being a literal identifier.

**Watch out:** the colon still renames the selected property. Writing `{ [selectedField] }` would try to create a variable named after the value, which is not valid for this use.

### Form 11: patterns in parameters and parameter defaults

**Syntax:** `function f({ a = 1, b }: Options = {}) { ... }`

**Example:** `createTask({ title, status = 'todo' } = {})` destructures its options parameter. The array-parameter example `([label, value]) => ...` also destructures at the function boundary.

**Output:** `form 11: { title: 'Read', status: 'todo' }` and `form 11b: page=42`

**Use it when:** a function accepts a named options object or a fixed-shape pair and should expose only the fields it uses.

**Watch out:** the default `= {}` protects a missing whole argument, while `status = 'todo'` protects a missing property. Without the outer default, calling `createTask()` would try to destructure `undefined`.

### Form 12: patterns in loops

**Syntax:** `for (const [key, value] of Object.entries(object)) { ... }`

**Example:** The code loops over both `Object.entries(scores)` and a `Map`, taking each two-item entry directly into `student, score` or `position, item`.

**Output:** `form 12 object: Ada 91`, `form 12 object: Bora 87`, `form 12 map: first email`, `form 12 map: second backup`

**Use it when:** an iterable naturally produces pairs, especially object entries, `Map` entries, or a function returning pairs.

**Watch out:** `for...of` gives values from the iterable. `for...in` gives property keys, so using `[key, value]` with `for...in` would not mean the same thing.

## Pitfalls

1. **Undefined/null on the right:** `const { a } = undefined` produced `pitfall 1: TypeError`, because there is no object from which a property can be read. Give the parameter a default or check first.
2. **Defaults do not replace null:** the output was `pitfall 2: fallback null`, because default initialisers run for `undefined` only; `null` is an actual value.
3. **Assignment needs parentheses:** `({ a: assignedTitle } = source)` produced `pitfall 3: new`. Parentheses are needed because a statement beginning with `{` can be parsed as a block rather than an assignment pattern.
4. **Shallow/reference behaviour:** changing `meta.done` through the destructured variable produced `pitfall 4: true`, because destructuring copies the reference to the nested object, not a deep clone.
5. **Array order versus object names:** both selected the word `second`, but the array used a position while the object used a property name. The output was `pitfall 5: second second`; changing array order would change the array result, while object order would not.

## Props and children (P1-P7)

These experiments are in `js/props.jsx` and `ts/props.tsx`, and every one is rendered with `renderToStaticMarkup`.

### P1 — props is one object

`CardA(props)` reads `props.title` and `props.children`. `CardB({ title, children })` destructures the same object in its parameter list. This is Form 5 (object properties by name) combined with Form 11 (a parameter pattern). Both rendered as `<section><h2>Hi</h2>text</section>`.

### P2 — children is only a prop

`<Card title="Same">text</Card>` and `<Card title="Same" children="text" />` rendered exactly the same markup. JSX content between tags is assigned to the `children` property of the one props object; it is not a second argument.

### P3 — possible children values

The JavaScript output showed a string as text, a number as text, one element as that element, and multiple elements next to each other. `undefined`, `null`, and `false` rendered as empty `<div></div>` content. A function is a JavaScript value (`typeof` was `function`) but React does not render a function as visible child content; it must be called by the component if that is the intended render-prop API.

### P4 — separating and forwarding props

`function Panel({ title, children, ...rest })` removes the fields it consumes and forwards the rest to `<section {...rest}>`. The output preserved `id="panel-1"` and `data-kind="demo"`. In `PanelExplicit`, the spread comes first and `className="explicit"` comes after it, so the explicit attribute wins over `className="from-rest"`. In general, later JSX attributes overwrite earlier ones.

### P5 — props or children?

The first `Layout` call used `header` and `footer` props, producing dedicated regions around the children. The second passed a complete structure as children, so the component's own header/footer slots were empty and the supplied elements appeared inside `<main>`. Props are useful when a component owns a stable layout contract; children are better when the caller needs flexible composition.

### P6 — defaults in a component

`function Badge({ label = 'default' })` rendered `default` for both an omitted label and `label={undefined}`. `label={null}` rendered an empty span, because Form 7 defaults apply only to `undefined`, not `null`.

### P7 — TypeScript prop types

`children?: ReactNode` explicitly permits strings, numbers, elements, `null`, and other React-renderable values. `PropsWithChildren<P>` adds the optional `children` field to an existing props type. `ComponentProps<'button'>` reuses React's native button props, including `type`, `disabled`, and event-related attributes. The TypeScript file includes an intentionally rejected invalid button type marked with the one allowed `@ts-expect-error`; JavaScript has no equivalent compile-time rejection.

## TypeScript topics T1-T5

- **T1:** `{ x: horizontal }` is a rename. The type annotation belongs after the whole pattern: `const { x: horizontal }: { x: number } = point`.
- **T2:** `[number, string]` is a tuple return type. `as const` makes `['ready', 2026]` a readonly tuple with literal types rather than a mutable `(string | number)[]`.
- **T3:** With `noUncheckedIndexedAccess`, an item taken from a general `string[]` can be `undefined`. The example uses `first ?? 'no item'` to handle that possibility.
- **T4:** An optional property stays possibly `undefined` when extracted without a default. The pattern `const { nickname = 'guest' }` narrows the local variable to a usable string.
- **T5:** A required `pages` property was intentionally omitted. TypeScript reports that `pages` is missing; the corrected object includes `pages: 12`. The expected-error comment documents this one deliberate compiler error.

|---|---|---|---|

| 2. rest | skipped item and rest array behave the same | tuple/rest annotation | value may be inferred too broadly |
| 3. swap | right side is evaluated before assignment | variables must have compatible types | assigning a string to a number variable |
| 4. defaults | fallback is used for `undefined` | optional tuple elements/types | `null` is not removed by a default |

## Bonus 2: Depth

### Iterables and evaluation order

An array pattern uses the iterable protocol, not an ordinary numeric-property lookup. For example, `const [first, second] = new Set(['red', 'blue'])` gets values in the Set's iteration order, while `const [a, b] = 'OK'` gets the characters `O` and `K`. A default expression is evaluated only when its value is `undefined`, and it is evaluated from left to right. Therefore `const [a = 2, b = a * 3] = []` gives `2, 6`; the second default can use the earlier binding.

### Other destructuring locations

Destructuring also works in `catch ({ message })`, in import/export bindings, in `for...of`, and in assignment targets such as `[box.left, box.top] = [10, 20]`. These are still patterns, but they occur at different grammar positions. `for...in` iterates property names, while `for...of` iterates values, which is why entry destructuring belongs naturally with `Object.entries` and `Map`.

### Readability trade-off

A short pattern such as `const { title, status } = task` removes noise. A very deep pattern with many renames can hide where data came from. In that case, a readable refactoring is to destructure one level at a time or keep a descriptive object name, even if it uses a few more lines.
